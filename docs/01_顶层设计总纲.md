## 1 背景、目标与范围

### 1.1 业务画像【默认，待用近一年项目清单核实】

- 客户以金融机构为主（保险、银行、证券），另有央企、协会和公共机构。
- 四个产品族：会议活动、培训学习、客户活动、出行福利（定制游、研学、游学、疗休养、团建）。
- 三种项目入口：招投标；框架入围后的二次比选或询价；直接委托（含老客户复购）。
- 一个项目通常组合多个服务模块（场地、讲师、交通、餐饮、物料、活动、现场服务等），资源分散，修改多轮，交付在线下。
- 项目沟通主要在企业微信群里进行（含客户和供应商的外部联系人），会话存档对接正在开发。

前期材料显示了业务范围，但真实收入结构和各产品族占比尚未核实。

### 1.2 要解决的三类摩擦

| 摩擦 | 现在的样子 | 本设计的主要对策 |
|---|---|---|
| 信息收集与维护 | 客户信息、聊天记录、报价、资源、策略散在群聊、个人电脑和个人记忆里；每次修改方案都要重新找背景 | 会话存档摄取 → 更新建议单 → 项目主卡；报价、资源、客户、证据各有唯一位置 |
| 创意辅助 | 方案参考靠个人经验，容易同质化 | GPT 按策划卡出实质不同的方向；优秀方案和策划片段持续沉淀 |
| 图文生成与编辑 | 方案、PPT、标书、汇报反复手工改，版本之间不一致 | 内容与版式分离、按模板生产、风格卡统一视觉、变更影响与一致性复核 |

### 1.3 设计目标

| 编号 | 目标 | 检验方式 |
|---|---|---|
| G1 | 一处事实：任何项目的当前有效信息只在一个地方，人和 AI 都从这里开始 | 换人或换平台，10 分钟内说清项目现状 |
| G2 | 三平台通用：所有 Skill 和资产在 GPT、WorkBuddy、豆包上都能用 | 同一测试用例在三个平台都通过同一验收标准 |
| G3 | 按难度分工：复杂判断、创意、视觉、工具设计由 GPT 承担；重复、文案、整理归档由 WorkBuddy 和豆包承担 | 每个 Skill 步骤都有默认层级，抽查实际执行与默认一致 |
| G4 | 全流程串通：从项目进入到复盘沉淀，每个环节都有方法、产出和回写位置 | D03 的 47 个场景都能找到主责 Skill、资产和人工关口 |
| G5 | 精简：首批产物最少，且足以串通全流程 | 首批每一项都能说出不可省的理由 |
| G6 | 可演进：新业务、新平台、新渠道、新字段都有扩展位和变更规则 | 设计外情况能按规则纳入，不用推倒重来 |
| G7 | 可控：金额、对外承诺、预订付款由人确认；资料按分级进入平台 | 每个状态升级和对外动作都有人工关口 |

### 1.4 约束与前提

- 聊天记录来自企业微信会话存档，接口由开发方实现；本设计只定义摄取口径（D04）。
- 三个平台都能生成图片和写代码；平台之间没有自动同步，默认通过共享文件和任务包交接。
- 第一期只做顶层设计；第二期起才建设规范、模板、Skill 和工具。

### 1.5 交付状态（2026-11-09）

- **第一期（设计）**：README、D01–D04，已确认。
- **第二至四期（建设）**：通用规则、9 个 Skill（含场景路由表和 47 张场景卡）、20 个模板、成本测算表、8 个工具、平台适配、检验样本、登记、使用手册、乐享接入方案，已建成并通过自动校验，清单见 D02。
- **尚未完成**：三个平台的实测、乐享登录验证、公司参数与品牌素材、真实样本、试点与培训。
- **不做**：历史资料的整体迁移。

## 2 指导思想

九条原则是后续所有设计的判断标准。每条写明含义、在设计中的体现和要避免的做法。

### 原则 1 以项目为中心，事实只存一处

- **含义**：业务信息要么属于某个项目，要么属于共享资产；每类事实只有一个权威位置，其他地方只引用编号，不另存一份。
- **体现**：项目主卡是项目当前事实的唯一入口；报价只在报价记录里；联系人只在联系人与群名册里。权威位置总表见 D03 第 2.2 节。
- **避免**：三个 AI 各记一套项目记忆；同一个价格在 PPT、表格和群聊里各是一个数。

### 原则 2 文件即接口，平台可替换

- **含义**：方法（Skill）、资产、模板和记录都是普通文件（Markdown、表格、原件），不依赖任何平台的私有记忆、数据库或专属功能来保存事实。
- **体现**：Skill 采用开放的 SKILL.md 格式；项目事实存放在共享的业务库；平台只是执行者，换平台不换资料。
- **避免**：关键规则只写在某个平台的自定义指令里；用平台记忆代替项目主卡。

### 原则 3 按难度分层分工，能力兼容

- **含义**：三个平台都能运行所有 Skill（兼容），但每个任务步骤都有默认执行层级（分工）。兼容保证韧性和互替，分工保证质量和成本。
- **体现**：每个 Skill 的步骤标注默认层级；主 Skill 负责路由、升级和降级（第 4 章）。
- **避免**：所有事都交给 GPT；或让执行层独立做方向性判断而没有复核。

### 原则 4 事实、判断、承诺分开，状态只由人升级

- **含义**：区分"谁说过""已确认""推断与建议""已承诺与已执行"。AI 可以提出状态变化，只有负责人能确认。
- **体现**：五套状态（6.5）；摄取进来的内容一律先是"待确认"。
- **避免**：把群里一句"预算可以考虑上调"写成预算已上调；把投标承诺写成公司业绩。

### 原则 5 计算靠表格，判断靠 AI，拍板靠人

- **含义**：数量、金额、税费、毛利由带公式的表格（或脚本）计算；AI 解释差异、找漏项、提替代方案；报价、选供应商、对外承诺由人决定。
- **体现**：成本测算表是唯一的算价工具；AI 输出中的金额必须注明来自哪个表格版本。
- **避免**：让模型心算总价；AI 直接把建议价写进对外报价单。

### 原则 6 最低充分，按需生长

- **含义**：首批只建设串通全流程所需的最少产物；新的 Skill、资产、字段先在真实工作中证明需要，再按准入标准加入；资产在项目收尾时沉淀，不做大规模历史迁移。
- **体现**：Skill 准入标准（7.7）；先模板后 Skill，先表格后系统。
- **避免**：先建二十个 Skill 和完整知识库，再开始使用。

### 原则 7 可追溯、可接续

- **含义**：每个成果都能追到所用资料的版本；每次任务结束留下交接卡；任何人、任何平台都能从主卡和交接卡接着做。
- **体现**：版本指针、来源字段、项目日志、交接卡、任务包。
- **避免**：只能靠"上次那个聊天窗口"继续工作。

### 原则 8 为变化留位置

- **含义**：可以预见的变化（新业务类型、新平台、新沟通渠道、新资源类别、新字段）都有扩展位和变更规则；没定的事显式登记，不默认假设。
- **体现**：四种标记、扩展位表、待定事项登记、版本号、模板里的扩展字段（第 11 章）。
- **避免**：把未经验证的分类写死；出现新情况只能推倒重来。

### 原则 9 数据分级，最少必要

- **含义**：资料按敏感程度分级，平台按级别准入；每个任务只给 AI 完成任务所需的最少资料。
- **体现**：数据分级（第 9 章）；任务包只带必要文件；摄取时识别并遮蔽个人信息。
- **避免**：为了方便，把全部聊天记录和名单发给所有平台。

## 3 顶层架构

### 3.1 五层结构与闭环

```
入口层   企业微信会话存档 │ 招标与客户文件 │ 供应商报价 │ 会议/电话纪要 │ 公开平台查询 │ 乐享知识库
            │  统一格式摄取（D04）与人工投递
            ▼
事实层   项目工作区（主卡、日志、原件、过程记录）＋ 共享资产（资源、报价、能力证据、客户、素材、名册）＋ 乐享（公司知识，按映射表）
            │  按任务读取：主卡 → 交接卡 → 必要资料
            ▼
方法层   主 Skill「项目总控」＋ 业务 Skill（首批 6 个，第二批 2 个）＋ 模板 ＋ 工具
            │  按分工路由（第 4 章）
            ▼
执行层   GPT：判断、创意、视觉、工具设计
         WorkBuddy／豆包：生产、文案、整理归档
         表格／脚本：计算、校验
         人：决定、承诺
            │
            ▼
成果层   方案、PPT、标书、报价单、执行手册、文案通知、视觉素材、结算资料、复盘
            │
            └── 人确认后回写事实层；项目收尾时沉淀到共享资产
```

治理贯穿各层：设计与规范文档、产物清单、扩展登记与待定登记、版本与变更记录、检验样本。

### 3.2 方法库与业务库分开存放【定】

| | 方法库 | 业务库 |
|---|---|---|
| 存什么 | 设计与规范、Skill、模板、工具、平台适配、检验样本（脱敏） | 项目工作区、共享资产、摄取收件箱 |
| 含客户事实 | 否 | 是 |
| 位置 | 本目录，建议用 Git 管理版本【默认】 | 公司共享存储，按权限访问【待定：DQ01】 |
| 怎样到达平台 | 作为 Skill 包导入，或由工具生成指令版 | 平台直接读取（有权限时），或通过任务包 |

分开存放的好处：Skill 可以放心导入任何平台；客户资料按数据分级单独控制；Skill 更新不影响项目记录。

### 3.3 一条事实的生命周期

摄取或录入 → 更新建议（带来源，状态"待确认"）→ 负责人确认 → 写入主卡、日志或资产 → 被任务读取 → 进入成果（标注依据版本）→ 发生变更时做影响检查 → 收尾时沉淀，或标记作废。

### 3.4 一次任务的生命周期

发起（口令或定时）→ 主 Skill 识别项目和任务 → 恢复上下文（主卡、日志近期条目、上一张交接卡）→ 判断层级与数据准入（在本平台执行，或生成任务包交给对应平台）→ 业务 Skill 执行 → 自检与复核 → 按命名规则保存成果 → 提出回写建议 → 生成交接卡。

### 3.5 目标中的一天（使用体验）

- **项目经理**：早上看各项目的更新建议单，只确认标为"需确认"的条目，每个项目约 5 分钟。
- **策划**：对 WorkBuddy 说"给 GPT 准备 018 的策划任务包"，到 GPT 里出三个方向；选定后对 WorkBuddy 说"按方向 B 出方案内容稿"，再请 GPT 审一遍。
- **资源采购**：把三家酒店的报价单交给 WorkBuddy："录入 018 的酒店报价并比较"，得到比较表和成本测算；有取舍问题时请 GPT 看。
- **客户在群里改了人数**：更新建议单把它标为变更 → "客户改了人数，查影响" → 变更影响单 → 负责人确认 → 改文件。
- **发送前**："发送前检查 018 全部文件"。
- **任何人接手**：打开主卡、日志和最近一张交接卡。

员工只需要记住三件事：主卡在哪、本岗位的五到八句口令、什么时候要自己确认。

### 3.6 内容分层：通用规则与具体场景【定】

所有方法内容分五层，每层只写一种东西。下层引用上层的编号，不复制上层的原文；冲突时上层优先（优先级见 skill-source/shared/00-index.md 第 2 节）。

| 层 | 回答什么 | 位置 | 写什么，不写什么 |
|---|---|---|---|
| 1 通用规则层 | 任何任务都必须遵守什么 | skill-source/shared/（D05、D06、D07、D09、D10） | 只写对所有场景都成立的规则；不写某个场景的步骤 |
| 2 路由层 | 这句话或这个事件属于哪个场景 | project-hub/references/routing.md | 47 个场景的触发、判别要点、一行路径；易混淆场景的判别规则和标准问法 |
| 3 场景层 | 这个场景按什么顺序经过哪些 Skill 和模式 | project-hub/references/scenarios/（9 组 47 张） | 每一步的 Skill·模式、层级、产出；人工关口；回写；分支。通用要求只引用编号 |
| 4 方法层 | 某个 Skill 在某种模式下怎么做 | 各 Skill 的 references/modes.md 等 | 单个 Skill 内的步骤和判断要点 |
| 5 素材层 | 用什么格式、参照什么内容 | templates/、策划卡、共享资产 | 格式和参照，不写流程 |

事实（项目和公司的具体信息）不属于任何一层，放在业务库和乐享。

### 3.7 从一句话到成果的路由路径【定】

以"018 客户把人数改成 55，还要加一场晚宴"为例：

1. **通用规则**：读平台身份声明（D06 §2）。
2. **路由层**：认出项目 018；按 routing.md 判别——人数变化 ≥ 10% 且增加了服务模块 → SC31 重大变更（不是 SC30 小修改）；项目阶段不是"执行中"（不是 SC37）。
3. **场景层**：打开 F-change.md 的 SC31，路径为 S06·M1〔T1〕→【人】→ S04·M1、M4〔T2、T3〕→ S05〔T2〕→ S06·M3〔T3、T2〕→【人】。
4. **方法层**：change-review 的 M1 按服务模块映射影响（人数 → M03、M04、M05、M11、M12、M07；晚宴 → M03、M04、M06、M08）。
5. **每一步前的检查**：本平台是 WorkBuddy（T2），M1 是重大变更（T1）→ 生成任务包交 GPT；GPT 不可用时降级执行并标注（D06 §3.2、§4.3；D07 §4）。
6. **素材层**：变更影响单用 TP04；修改文件用 TP12、TP13、TP14；测算用 X01。
7. **收尾**：通用复核清单、交接卡、回写建议（D06 §8–§10）。

## 4 分工设计

### 4.1 对大方向的看法

你给出的方向我认同：GPT 承担复杂工作、图片生成与编辑、高难度理解、顶层工具的设计与优化；WorkBuddy 和豆包同档，承担重复性、文案、整理归档、难度不高或中文语境的工作。在此基础上补充四点：

1. **按任务步骤分工，而不是按业务环节分工。** 同一个环节里通常既有判断也有生产。以标书为例：读懂评分规则、找出实质性条款和废标风险是 GPT 的事；按目录组装响应文件、匹配证据是执行层的事。所以每个 Skill 的每一步都单独标层级。
2. **GPT 的产出以"可复用"为主。** GPT 最有价值的产出是一次判断、多次使用的东西：策划方向、风格卡、模板、Skill、工具。执行层按这些产出高频生产。这样 GPT 用量少、效果稳定，也符合它在账号、费用和数据上的限制。
3. **兼容是为了韧性和互替，不是平均分配。** 所有 Skill 在三个平台都能运行，是为了某个平台不可用、额度不够或资料不能进入某个平台时可以换平台执行。平时仍按默认分工。
4. **WorkBuddy 和豆包同档可互换，但一个项目只指定一个主执行平台。** 两者能做同样的事；如果同时写同一份正式文件，会出现两套"最终版"。主执行平台登记在项目主卡里。

另有两个提醒：

- **中文语境不等于低难度。** 标书里的方案阐述、对客汇报讲稿都是高要求的中文成文。做法是执行层成文、GPT 审查，或 GPT 定框架、执行层成文，而不是只交给其中一边。
- **数据边界会限制 GPT 能看的资料。** GPT 的工作对象默认是脱敏后的任务包。某个任务离不开保密原件或个人信息时，改由准入平台执行，或由人处理（第 9 章）。

### 4.2 四个执行层级【定】

| 层级 | 任务特征 | 典型任务 | 默认执行者 |
|---|---|---|---|
| T1 判断与创造 | 输入含糊或冲突；多约束取舍；需要创意或专业判断；结果影响方向或风险 | 招标文件深度解读；投标与接单判断；策划方向与体验设计；方案审查；复杂变更影响；风格卡与主视觉；图片精修与合成；Skill 与工具的设计和优化；投标与报价策略 | GPT |
| T2 规则化生产 | 方向已定；有模板或明确简报；中文成文；批量与整理 | 沟通记录增量整理；需求矩阵填写；询价单；报价归一；按模板写方案、PPT、标书；文案与通知；按风格延展图片；归档命名；周报 | WorkBuddy 或豆包 |
| T3 确定性处理 | 结果可以算出来，或可以按规则核对 | 成本测算与情景；报价有效期检查；跨文件数字一致性；格式转换 | 表格公式与脚本（T1 设计，T2 运行） |
| T4 决定与承诺 | 对外或不可逆；涉及金额、合同、安全 | 投不投；选方向；对外报价；选供应商；预订付款；提交与发送；确认变更；状态升级 | 人 |

### 4.3 平台角色

| 平台 | 主责 | 默认不承担 | 接触资料的方式 |
|---|---|---|---|
| GPT（ChatGPT、Codex） | T1 全部；关键视觉（风格卡、主视觉、概念图、图片编辑）；Skill、模板、工具的设计与优化；关键成果终审 | 批量格式化、日常归档、逐条整理 | 任务包（按数据分级筛选）；Codex 可直接读方法库 |
| WorkBuddy | T2；企业微信里的日常操作：处理沟通摘要、提出更新建议、归档命名、按模板生产、定时提醒与周报 | 未经升级的方向性判断 | 直接读写业务库（有权限时）；在企业微信内调用 |
| 豆包 | T2，与 WorkBuddy 同档；中文文案与对客表达、手机端快速任务；第二执行平台与备用 | 同上 | 任务包，或其可连接的文档空间 |
| 表格与脚本 | T3 | 判断 | 方法库中的工具 |
| 人 | T4；资产维护；状态确认 | 重复转录 | 全部（按权限） |

**主执行平台默认值**：WorkBuddy【默认，待第二期实测：DQ02】。理由：会话存档和项目群都在企业微信，WorkBuddy 可以在企业微信内调用，也可以导入 SKILL.md 技能包。豆包默认负责文案类成果，并作为第二执行平台。每个项目可以在主卡里改设置。

### 4.4 升级、降级与降级执行【定；阈值待定】

**执行层升级到 GPT**，满足任一项即升级：

- 资料之间有冲突，并且会影响方案、报价或承诺；
- 需要在多个可行方案之间取舍，或客户诉求含糊（例如"更高级，但预算不变"）；
- 重大变更：总价变化 ≥ 5%、人数变化 ≥ 10%、日期或地点或主要资源变化、增减服务模块、涉及安全（阈值【待定：DQ05】）；
- 新类型任务，没有模板或先例；
- 同一成果自检两次仍不通过；
- 对外关键成果的终审（见 4.7）。

**GPT 降级到执行层**：方向和结构已定，后面是按模板成文、出变体、排版、归档或批量重复。此后 GPT 只抽检或终审。

**升级的做法**：执行层由主 Skill 生成任务包（交接卡、必要资料、期望产出），交给 GPT；GPT 的产出按命名规则存回业务库。

**降级执行**：GPT 不可用（账号、网络、额度），或资料不允许进入 GPT 时，T1 步骤可以在执行层运行。成果开头标明"降级执行：未经 T1 审查"，并列入待确认，由负责人决定直接采用还是补审。

### 4.5 图片与代码的分工

| 图片任务 | 默认 | 说明 |
|---|---|---|
| 风格卡（色彩、构图、字体、元素、禁用项、参考图） | GPT | 每个项目或每类产品一次，之后复用 |
| 主视觉、封面、概念图、场景示意 | GPT | 关键对客视觉 |
| 图片编辑：局部修改、合成、修图、风格统一 | GPT | |
| 按风格卡延展尺寸、版式、海报、物料、配图 | 执行层 | |
| 带中文文字的图片 | 【待定：DQ10】 | 各平台中文字形效果差异大，实测后定默认平台 |
| 真实场地、酒店、历史活动照片 | 人 | 用有来源和授权的实景，不用 AI 图片替代 |

所有 AI 图片都标注"创意示意"，并记录生成平台、提示词和用途，存放在项目的 04_策划与设计。

| 代码任务 | 默认 |
|---|---|
| 设计：成本测算模型、一致性检查、指令版生成、提醒规则、摄取摘要转换 | GPT（Codex） |
| 运行和小改：按说明运行、改参数、更新数据 | 执行层 |
| 规则 | 计算以表格公式为准；脚本优先只用标准库 Python（处理 XLSX 时可用 openpyxl）；每个工具都有说明和手工替代办法 |

### 4.6 正式文件只有一个主责【定】

- 每类对外成果（方案、PPT、标书、报价单、执行手册）在一个项目里只有一个主责平台和一个负责人。
- 其他平台只提供输入：方向、视觉、文案片段、审查意见，不产出平行的"最终版"。
- 主责登记在项目主卡的"分工设置"里。

### 4.7 复核分级【默认】

|---|---|---|---|---|
| 内部工作稿 | 必做 | — | — | — |

| 对客方案、PPT | 必做 | 必做 | 首版和重大修改 | 项目经理 |

审批人按公司组织确认【待定：DQ06】。

### 4.8 人工关口【定】

AI 只能准备、建议和起草。以下动作必须由人完成或确认：是否立项跟进；是否投标或接单；方向选择；供应商选择；对外报价；提交标书和发送对外文件；确认客户变更；签约；预订和付款；现场重大调整；验收与结算确认；任何状态升级；案例和素材能否对外使用。

### 4.9 角色【默认】

| 角色 | 主要职责 | 常用平台 |
|---|---|---|
| 负责人 | 审批报价、投标、重大变更；确认数据政策 | 看周报和审批材料 |
| 项目经理 | 确认主卡、对客沟通、推进项目 | WorkBuddy |
| 策划 | 方向与方案 | GPT＋执行层 |
| 资源采购 | 询价、报价记录、供应商确认、资源档案 | WorkBuddy |
| 商务投标 | 标书、能力与证据库 | GPT＋WorkBuddy |
| 执行 | 执行手册、现场记录 | WorkBuddy；手机端豆包 |
| 财务 | 成本口径、结算 | 表格 |
| AI 协同负责人（内部，可兼任） | 收集问题、维护名册与素材库、管理平台账号 | 全部 |
| 建设方（你） | 设计、Skill 与工具建设、校验、迭代 | GPT（Codex）为主 |

一人可以兼多个角色；职责不能交给 AI。

### 4.10 分工写在哪里

分工规则只有一个来源：D06《分工、路由与复核规则》（第二期以本章为依据编写）。它同步进主 Skill 的共用规则；每个业务 Skill 在步骤里引用层级；项目主卡的"分工设置"把它落到具体项目；D11 使用手册向员工讲清楚。四处引用同一来源，不各写一套。

### 6.3 四种项目记录

**项目主卡（TP01）** 分九块：

1. 身份：项目编号、客户与部门、项目名称、入口类型、所属框架、关联项目、产品族、客户目标（一主多次）、负责人、关联群聊。
2. 分工设置：主执行平台、文案平台、GPT 任务负责人、各类成果的主责。
3. 当前有效条件：日期、地点、人数、预算口径、服务模块、硬性要求、评分要点。每条带状态和来源。
4. 方向与策略：选定方向、差异化要点、客户偏好、竞争情况、报价策略。
5. 待确认事项：问题、提出人、需要向谁确认、截止时间、负责人。
6. 资源与报价摘要：引用报价编号和成本表版本。主卡里出现的金额必须注明来源版本；与来源不一致时以来源为准。
7. 版本指针：当前有效的需求版本、方案、PPT、报价、标书、执行手册。
8. 下一步与风险：关键节点、待办、风险和红线。
9. 扩展字段与处理位置：沟通记录已处理到哪一条消息；暂时无法归类的信息。

**项目日志（TP02）**：时间、类型（决定、变更、事件、提交、确认）、内容、来源（消息编号或文件）、记录人、影响。只追加，不改写。

**任务交接卡（TP03）**：项目、任务、依据版本、已确认与待确认、本次产出、限制（数据级别与红线）、下一步、执行平台与层级、所用 Skill 及版本。

**变更影响单（TP04）**：变更原话与来源 → 确认状态 → 涉及的服务模块 → 受影响的资源、成本、日期、文件和承诺 → 需要重新核实的事项 → 需要修改的文件 → 审批 → 发布新版。

## 7 Skill 体系

### 7.1 总览

1 个主 Skill 加 8 个业务 Skill。首批（第三期）建设主 Skill 和 S01–S06。S07、S08 在第四期建设：先做模板 TP17–TP19，使用频率证明需要后再做成 Skill；第四期之前，执行和收尾工作先用公司现有的表格，由 S05 整理（D03 第 1 章）。所有 Skill 共用一套规则（7.4），分工层级标在每个步骤上。

### 7.2 主 Skill：项目总控（S00 `project-hub`）

主 Skill 在每次任务中都会加载，所以只做"总控"，内容保持精简：正文建议不超过 200 行，细节放 references。

| 职责 | 说明 |
|---|---|
| 新建项目 | 分配编号；按模板建工作区和主卡初稿；登记项目总表和群映射 |
| 识别与恢复 | 认出项目和任务；读主卡、日志近期条目、上一张交接卡 |
| 路由 | 选择业务 Skill；按分工规则判断层级；检查本平台是否是该层级的默认平台、资料是否允许进入本平台 |
| 生成任务包 | 需要交给别的平台时，打包交接卡、Skill 指令版和必要资料 |
| 共同规则 | 在每次任务中执行状态、来源、命名、数据准入规则 |
| 复核与收尾 | 按复核分级自检；保存成果；提出回写建议；生成交接卡 |
| 简单查询 | "018 现在什么情况"、本周项目周报等，直接完成 |

**平台身份**：各平台的加载说明里写明"当前平台"和"本平台默认层级"，主 Skill 据此决定在本平台执行，还是生成任务包交给别的平台。

### 7.3 业务 Skill

| 编号 | Skill | 批次 | 何时用 | 主要产出 | 步骤层级 | 人工关口 |
|---|---|---|---|---|---|---|
| S01 | 资料收录与项目更新 `intake-update` | 首批 | 沟通摘要到达；收到文件或纪要；"更新项目 018" | 更新建议单（新事实及来源与状态、待确认、待办、变更触发、资源与客户线索、归属建议）；文件归档与分级 | 抽取整理 T2；冲突与含糊处 T1 | 确认写入 |
| S02 | 需求与标书解析 `brief-analysis` | 首批 | 新采购文件、框架订单通知、直客需求 | 需求与评分矩阵、实质性条款与废标风险、资格证据清单、澄清问题、参与判断要点；全量、快速、澄清三种模式 | 全量模式的解读 T1；矩阵与清单 T2；快速模式默认 T2，与历史订单不同之处升级 T1 | 参与决定 |
| S03 | 策划与方案设计 `planning-design` | 首批 | 需要方向、方案结构、视觉或方案审查 | 2–3 个实质不同的方向及对比、方案结构（模块组合、行程、议程、课程）、风格卡、主视觉、审查意见 | T1 | 方向选择 |

### 7.4 共用规则

共用规则只在 `skill-source/shared/` 维护一份，由同步工具（X03）复制进每个 Skill 包；复制件不手改。这沿用 zhishiku2.0 的做法。内容包括：状态与来源规则、编号命名与版本规则、分工与路由摘要、数据分级与准入、交接卡与任务包格式、通用复核清单、服务模块摘要。

模板的源文件统一放在 `templates/`，同样由 X03 复制进用到它的 Skill 包。

### 7.5 Skill 包结构【定】

```
{skill-name}/
├── SKILL.md          frontmatter 只写 name 和 description；正文见 7.6
├── references/       详细方法、判断要点、示例
│   └── shared/       共用规则（同步生成，不手改）
├── templates/        本 Skill 用到的模板（同步生成，不手改）
├── scripts/          可选工具，每个都有手工替代办法
└── agents/           可选的平台元数据（如 Codex 的 openai.yaml），其他平台忽略
```

包内的文件名一律用 ASCII（打包导入的兼容性），内容用中文。

### 7.6 SKILL.md 必须写清的九项

前七项来自前期设计，后两项是为兼容和分工新增的：

1. 何时使用、何时不用（与相邻 Skill 的边界）
2. 输入：必需和可选；缺什么仍可继续，缺什么只能给出有条件的结论
3. 调用哪些资产和模板
4. 处理步骤：每一步标默认层级（T1–T4）
5. 产出：内容、格式、文件名、保存位置、版本状态
6. 验收：完成标准、必须解决的错误、常见失败
7. 回写：哪些是新事实，哪些是待验证的经验，哪些只是本次草稿
8. 平台差异与替代：某项能力不可用时怎么做
9. 版本与口令：版本号、变更记录、给员工用的标准说法

动态内容（报价、资源可用性、联系人、项目条件）不写进 Skill。Skill 规定"怎样核"，具体内容从资产读取。

### 7.7 准入、拆分与下线【定】

- **新建 Skill**：以下四项都满足才建——多个项目里反复出现；输入输出清楚；方法稳定、写得下来；能用样本验收。并且现有 Skill 加模板解决不了。
- **不满足时**：先做模板或口令，或在已有 Skill 的 references 里加一节。
- **拆分**：同一个 Skill 里出现判断逻辑或输入输出实质不同的分支，并且各自高频。
- **合并或下线**：连续三个月很少使用，或总是被别的 Skill 替代。

## 8 跨平台兼容

### 8.1 兼容目标【定】

同一份 Skill 和资产在三个平台都能完成同一个测试任务，产出达到同一个验收标准。平台之间的差异只出现在加载方式和个别能力上，记录在兼容矩阵（D08）里，不写进 Skill 正文（"平台差异与替代"一节除外）。

### 8.2 平台现状（2026-11-09 查证）

| 平台 | Skill 加载 | 依据 | 待核验 |
|---|---|---|---|
| GPT | ChatGPT 和 Codex 原生支持 SKILL.md（基于开放的 Agent Skills 标准）；ChatGPT 桌面端可直接使用独立技能，网页与手机端通过插件分发；ChatGPT 用 @ 调用，Codex 自动扫描 `.agents/skills` | [OpenAI 技能文档](https://learn.chatgpt.com/codex/skills)、[OpenAI Academy](https://academy.openai.com/public/resources/skills) | 团队内的共享与分发方式 |
| WorkBuddy | 可导入 SKILL.md 技能包，导入时做格式校验和安全扫描；可在企业微信内调用 | [腾讯云文档](https://cloud.tencent.com/document/product/1759/129563)、[爱范儿报道](https://www.ifanr.com/1684200.md) | 技能包大小限制；能否读写腾讯文档或共享盘 |
| 豆包 | 未查到原生导入 SKILL.md 的官方说明；豆包工作可以根据材料生成和修改文档、PPT、表格 | [飞书官网：豆包工作](https://www.feishu.cn/content/article/7677519271848610746) | 是否支持技能包；智能体指令的长度上限；文件读写方式 |

结论：GPT 和 WorkBuddy 按原生技能包设计；豆包先按"项目或智能体指令"和"任务包"两种方式设计，实测支持原生技能后再切换。这也说明 Skill 不能依赖任何一个平台的专属功能。

### 8.3 编写约束【定】

1. frontmatter 只用 name 和 description；name 用小写英文加连字符，description 用中文写清何时使用。
2. 正文用中文 Markdown；写能力（"读取文件""生成表格""生成图片"），不写某个平台的工具名。
3. 用到特定能力的步骤都写替代办法：不能写文件时，输出完整内容并注明保存路径；不能运行脚本时，用表格模板或手工步骤。
4. 计算以表格公式为准，脚本只做辅助；脚本优先只用标准库 Python，处理 XLSX 时可以用 openpyxl，缺少时给出手工替代。
5. 不依赖平台记忆；每次都从主卡和交接卡开始。
6. 文件用 UTF-8 编码和相对路径；Skill 包内的文件名只用 ASCII。
7. SKILL.md 保持精简，长内容放 references 按需读取。
8. 共用部分只在 shared 维护，同步进各包。
9. 每个 Skill 写版本号；交接卡记录执行平台和 Skill 版本，用来发现平台之间的版本不一致。

### 8.4 三种加载方式

| 方式 | 做法 | 适用 |
|---|---|---|
| 原生技能 | 直接导入或安装 Skill 包 | GPT、WorkBuddy；豆包如果实测支持 |
| 项目或智能体指令 | 把 Skill 的"指令版"作为项目或智能体指令，references 和模板作为知识文件 | 不支持原生技能的平台；需要固定工作环境时 |
| 任务包 | 交接卡、指令版单文件和必要资料，作为一次性任务发送 | 任何平台；跨层级交接；临时账号 |

"指令版"由工具 X03 从 Skill 包自动生成，是单个文件，保证和原生版内容一致，不手工维护。

### 8.5 任务包：跨平台交接的统一形式【定】

- **内容**：交接卡（必有）、所用 Skill 的指令版、必要资料（按目标平台的数据准入筛选或脱敏）、产出要求（文件名、格式、保存位置）。
- **生成**：由主 Skill 在任何平台生成；执行层可以替策划自动打包。
- **回收**：产出按命名规则存回项目工作区；平台不能直接写入时，由发起人保存。
- **用途**：执行层升级给 GPT；GPT 降级交给执行层；平台无法直接访问业务库时。

### 8.6 内容与版式分离【定】

各平台先产出结构化的内容稿：方案按章节，PPT 按页，标书按招标文件目录。然后再套用公司模板排版。最终文件用 DOCX、PPTX、XLSX、PDF；中间稿用 Markdown 和 CSV。哪个平台排版效果最好，第二期实测后再定默认【待定：DQ10】。

### 8.7 图片与代码的兼容

- **图片**：风格卡用文字写清色彩值、构图、字体、元素、禁用项，另附参考图，任何平台的图片模型都能照着做；成图记录平台、提示词、用途和"示意"或"实景"。
- **代码**：工具放在方法库里，有说明和手工替代办法；表格模板在任何平台和人手里都能用。

### 8.8 第二期的平台核验清单

每个平台核验以下各项，结果写入兼容矩阵，并定出每个平台的默认加载方式：

- Skill 的加载方式与大小限制
- 能读写哪些位置：本地、共享盘、企业微信微盘、腾讯文档、飞书
- DOCX、PPTX、XLSX 的生成质量，能否填充公司母版
- 图片生成、编辑和中文字效果
- 能否运行代码，能用哪些库
- 扫描版 PDF 的文字识别（前期 44 份 PDF 共 2427 页，其中 1506 页没有取到文字）
- 项目级指令与知识文件
- 数据驻留、留存与企业管理
- 账号、网络与费用

## 9 数据分级与平台准入【框架定；准入默认值待负责人确认：DQ04】

| 级别 | 内容示例 | 默认准入 | 处理要求 |
|---|---|---|---|
| L1 公开 | 公开招标公告和采购文件、公开网页、公开价格 | 三个平台 | 无 |
| L2 内部 | 方案、内部策略、不含供应商身份的成本结构、标准响应段落 | 三个平台（企业账号） | 优先去掉客户身份 |
| L3 保密 | 非公开采购文件、客户内部资料、供应商报价与底价、合同 | 按客户保密要求和平台条款逐项允许；默认用国内平台；GPT 只处理脱敏版本 | 记录允许的范围 |
| L4 个人敏感 | 参会和出行名单、证件、联系方式、未成年人信息、健康信息 | 默认只用表格和本地工具处理；确需 AI 时只用负责人指定的平台，并用编号代替姓名；不进入 GPT | 摄取时识别并遮蔽 |

- 文件和消息都带级别标签：摄取时初判，人可以修正。
- 主 Skill 在生成任务包和执行任务前检查准入；不允许时，改用准入平台、先脱敏，或交给人处理。
- 客户合同或采购文件里的保密条款优先于上表。
- GPT 是境外服务，涉及个人信息出境有专门的合规要求；客户团队如何访问 GPT 也需要先解决（DQ03）。

## 10 外部信息来源

### 10.1 聊天记录摄取（要点）

完整约定见 D04《聊天记录摄取口径》。要点如下：

- **范围**：只摄取在名册里登记过的群（客户群、供应商群、项目内部群）；未登记的会话不进入业务库。开通存档所需的告知与同意，由公司按企业微信规则和法律要求处理。
- **统一格式**：无论来源是会话存档、手工投递，还是将来的邮件或电话录音，都转成同一种消息记录，后面的处理不随来源变化。
- **两种输出**：统一消息记录（给工具用，存于摄取系统）；按项目、按日、按群的沟通摘要（给人和 AI 用，存入项目的 02_沟通记录）。
- **归属**：群对应客户和项目；一个群对应多个在办项目时，由 S01 提出归属建议，无法判断的进入"待归属"。
- **媒体**：图片做文字识别，语音转写，文件保存原件并抽取文字，合并转发的聊天记录展开；撤回的消息标注"已撤回"，不作依据。
- **敏感信息**：识别 L4 个人信息，在摘要中遮蔽。
- **时效**：定时批次（默认工作日每天两次）加按需拉取（"更新项目 018"）；项目进入执行阶段后可以提高频率；现场变更直接用口令发起，不等摄取。
- **处理**：S01 只读上次处理之后的新增内容，产出更新建议单。建议单分两类：只有"需确认"（影响当前条件的信息、决定、变更、待办）需要人确认，"仅记录"类不必逐条确认。摄取不改变任何事实的状态。
- **上线前**：S01 先用手工投递按同一格式运行；接口上线后直接切换，不用改 Skill。

### 10.2 乐享知识库（要点）

完整方案见 D12《乐享知识库接入方案》。要点如下：

- **可行**：乐享有官方 MCP 服务；接入地址在线，认证为标准 OAuth（也支持会话令牌）；权限跟随登录账号。
- **定位**：先作为只读的公司知识来源；部分共享资产是否放进乐享，试点后决定；项目工作区暂不放进乐享。
- **一处事实**：乐享中的内容按 D05 §2.3 的映射表登记权威位置，业务库只引用、不复制；不能连接的平台用快照（D05 §2.4）。
- **安全**：AI 默认只读；写入只在 AI 产出区并经审核；令牌不进方法库（D07 §5、§6）。
- **待做**：企业乐享 code 与登录后的验证清单（D12 §8；DQ13–DQ17）。
