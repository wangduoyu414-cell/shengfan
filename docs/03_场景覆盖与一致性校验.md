## 3 情景推演

### WT1 框架客户二次比选，48 小时内响应

**过程**

1. 客户在框架客户群里发出需求 → 批次摄取或"更新项目" → S01 识别为新订单需求，建议立项。
2. S00 新建项目 2026-031，所属框架 2025-007；在名册中把它登记为该群的活跃项目。
3. S02 快速模式（T2）：对比该客户最近三次订单（在 A01 中按客户、产品族、城市筛选），列出不同之处；不同之处涉及评分或资格时升级 T1。
4. S04 从 A04 取同城同类资源的近期报价并检查有效期；过期的生成询价单；用 X01 测算。
5. S05 以上次中选的方案为底稿改写（T2）；GPT 只审查差异部分。
6. S06 一致性检查 → 负责人审批报价 → 发送。

**发现与处理**

- 同一个框架群里同时有多个订单，消息和报价的归属会混 → F2：每次订单单独立项，用"所属框架"关联；D04 增加归属建议和待归属。
- 快速模式如果默认 T1，GPT 用量大且慢 → F3：快速模式默认 T2。
- 找"相似历史项目"需要能筛选的字段 → A01 已包含所属框架、产品族、城市、人数、日期字段（D01 6.4），完整字段在 D05 落实。

### WT2 公开招标项目

**过程**

1. 商务把采购文件放进 01_原始资料（L1）→ S00 新建项目。
2. S02 全量模式：GPT 解读资格、评分、实质性条款、废标风险和格式要求（T1）；执行层生成需求与评分矩阵、资格证据清单（T2），对照 A05 检查有效期和适用主体。
3. 负责人决定投标（T4）。
4. S03 出方向；S04 报价；S05 按招标文件目录生成响应框架并组装（T2），引用证据编号。
5. S06 一致性检查和废标项检查（T3/T2）→ GPT 终审（T1）→ 签章提交（T4）。

**发现与处理**

- 扫描版采购文件能不能识别还不知道（前期 44 份 PDF 共 2427 页，其中 1506 页没有取到文字）→ F12：列入平台核验清单。
- 证照过期常常到最后才发现 → S02 在投标判断阶段就产出资格证据清单并检查有效期（已在 S02 的产出中）。

### WT3 直客定制游，多轮修改

**过程**

1. 客户在群里提出需求 → S01 → S02 澄清模式按出行福利策划卡的必问问题列出问题（T2）→ 项目经理发问。
2. S03 出三个方向（T1）→ 客户选 B。
3. S04、S05 出方案和报价。
4. 客户说"人数从 40 改到 55，改成两天一晚，加一场晚间交流会" → S01 标为变更触发 → S06（重大变更，T1）：涉及 M03、M04、M05、M06、M08，列出需要重新核实的房量、车辆、场地和设备 → S04 重算 → 负责人确认 → S05 改文件 → S06 一致性检查 → 发送。

**发现与处理**

- S06 需要知道每个文件引用了哪些事实 → 主卡的版本指针加上成果按服务模块组织（D01 6.7）：变更先映射到模块，再找到文件。已在设计中。
- 客户口头说"大概 55 人"时，信息状态是"待确认"，在确认前不触发重新报价 → 原则 4 已覆盖；S01 的规则里写明（D05 落实）。

### WT4 研学项目（含未成年人名单）

**过程**

1. 学校在群里发学生名单（Excel）→ 摄取识别为 L4，摘要中遮蔽；原件只存在 01_原始资料，并限制权限。
2. 分组和房间分配用表格工具（T3）；执行层需要处理时用编号代替姓名；名单不进入 GPT。
3. S03 使用出行福利策划卡，必查安全、监护、保险、交通时长和应急安排。
4. S07 出执行手册和家长通知（通用通知，不含个人信息）。

**发现与处理**

- 原设计没有写清"名单类任务怎么做" → F11：L4 用表格处理，执行层用编号代替姓名，不进入 GPT。

### WT5 执行中的现场变更（下雨，户外活动改室内）

**过程**

1. 现场人员在内部群里说明情况，同时对 WorkBuddy 说"018 户外拓展因雨改室内，查影响"。
2. S06 快速影响检查：场地、物料、流程、成本、取消损失（T2）；需要替代方案时升级 T1，GPT 不可用时降级执行。
3. 项目经理决定（T4）→ S05 出客户通知 → 记入项目日志。

**发现与处理**

- 如果依赖每日批次摄取，现场信息要到第二天才进入系统 → F4：增加按需拉取；执行阶段可以提高摄取频率；现场变更用口令直接发起，不等摄取。

### WT6 投标截止日 GPT 不可用

**过程**

1. 终审需要 T1，但 GPT 的账号或网络不可用。
2. 在 WorkBuddy 上以降级执行运行 S06 的终审步骤，成果标明"降级执行：未经 T1 审查"，列入待确认。
3. 负责人决定是否提交。

**发现与处理**

- 不同平台可能运行不同版本的 Skill，降级结果无法比较 → F8：交接卡记录执行平台和 Skill 版本；兼容矩阵记录各平台的部署版本。

### WT7 员工查询公司资料（乐享）

**过程**

1. 员工问"我们做过类似的研学吗" → project-hub 认出 SC47。
2. S00·P3：查 D05 §2.3 映射表，确定案例的权威位置（A07 或乐享）。
3. 本平台（WorkBuddy）已连接乐享：关键词检索，结果不理想时语义检索，读取正文。
4. 回答注明来源（乐享｜条目名｜更新时间）和能否对外使用。

**发现与处理**

- 映射表建立之前，权威位置不明确 → 未登记的乐享内容只作参考，不作为权威（D05 §2.3）。
- GPT 没有连接乐享时 → 在交接卡中列出检索词，由已连接的平台补快照（D06 §3.4）。

## 4 使用体验检查（CK10）

| 角色 | 每天要做的 | 要记住的 | 风险与对策 |
|---|---|---|---|
| 项目经理 | 确认更新建议单（每个项目约 5 分钟）；关键节点发口令；发送前看复核结果 | 主卡位置、约 8 句口令、自己的确认点 | 每天确认变成负担 → F10：建议单分"需确认"和"仅记录"，只确认前者 |
| 策划 | 在 GPT 里出方向和视觉；交给执行层出稿；看审查意见 | 约 6 句口令 | 为 GPT 准备资料麻烦 → F7：执行层自动打包任务包 |
| 资源采购 | 把报价单交给执行层录入和比较；确认价格状态；维护资源档案 | 约 5 句口令、价格状态 | 报价过期没人管 → 报价有效期字段；第五期的提醒工具 X05 |
| 商务投标 | 用 S02、S05 出标书；维护证据库 | 约 5 句口令、证据状态 | 证据库初建工作量大 → 第二期只放常用证据，之后按标书逐步补 |
| 执行 | 用执行手册；现场用口令记录异常 | 约 4 句口令 | 现场没有电脑 → 手机端豆包，或企业微信里的 WorkBuddy【待实测】 |
| 负责人 | 看周报；审批 | 审批点 | — |

**结论**：没有哪个角色需要把同一信息录入两次——沟通由摄取进入，报价单由执行层录入。每个角色只需要记住主卡的位置、本岗位五到八句口令和自己的确认点。
