# 聊天记录摄取口径

版本 v0.2（预留接口约定） · 2026-11-09 · D04

---

## 0 说明

- **作用**：约定企业微信会话存档（以及其他沟通渠道）的聊天记录以什么范围、什么格式、什么频率进入业务库；开发方据此实现，S01「资料收录与项目更新」据此处理。
- **读者**：会话存档对接的开发方、建设方、项目经理（维护名册和映射）。
- **定位**：这是接口约定，不规定开发方内部怎样实现。企业微信的字段名和消息类型以官方《会话内容存档》开发文档为准，本文只定义输出格式和处理要求。
- **状态**：v0.2，字段为【默认】，需要和开发方逐项对齐（第 12 章）。参考实现见 `tools/digest_from_jsonl.py`（X06），样本见 `tests/V01/intake-update/sample_messages.jsonl`。
- **上位文件**：D01 第 9、10 章（数据分级、摄取要点）；名册见 D01 6.4 的 A08。

---

## 1 原则

1. **原样保存与加工使用分开**：原始存档由摄取系统受控保存；业务库只放按项目整理的摘要和必要的原件。
2. **只摄取登记过的会话**：在名册里登记且标为"摄取"的群才进入业务库。
3. **统一格式**：所有来源都转成同一种消息记录，后续处理与来源无关。
4. **可追溯**：每条记录都保留原始消息编号；摘要中的每一行都能回到原记录。
5. **幂等**：同一条原始消息不论处理多少次，只产生一条记录。
6. **最少必要**：识别个人敏感信息并在摘要中遮蔽；AI 只读项目范围内的摘要。
7. **摄取不改变事实状态**：进入业务库的内容都是"待确认"的材料，状态由人确认。

---

## 2 范围

**纳入**

- 名册（A08 群与项目映射）中登记、并且"是否摄取"为"是"的群：客户群、供应商群、项目内部群、混合群。
- 单聊：默认不纳入【待定：AL5】；需要纳入时按人登记。

**不纳入**

- 未登记的群和单聊。
- 与项目无关的员工内部会话。
- 企业微信记录为"不同意存档"的对象的消息（以企业微信的同意状态为准）。
- 红包、表情等没有业务内容的消息（丢弃或只计数）。

**前提**：会话存档的开通，以及员工和外部联系人的告知与同意，由公司按企业微信规则和法律要求处理。

---

## 3 数据流

```
企业微信会话存档
  → 原始存档库（摄取系统，受控）
  → 标准化：转成统一消息记录
  → 映射与归属：群 → 客户、项目
  → 媒体处理：图片识别、语音转写、文件抽取、合并转发展开
  → 敏感信息识别与遮蔽
  → 输出：统一消息记录（留在摄取系统）＋ 项目沟通摘要（写入业务库）
  → S01 资料收录与项目更新 → 更新建议单 → 人确认 → 主卡、日志、共享资产
```

## 4 统一消息记录【默认】

每条消息一条记录，采用 JSON Lines 格式，UTF-8 编码。

| 字段 | 必填 | 说明 |
|---|---|---|
| record_id | 是 | 本系统的记录编号，全局唯一 |
| source | 是 | 来源：`wecom_archive`、`manual`；`email`、`feishu`、`phone`、`meeting` 等【预留】 |
| source_msg_id | 是 | 原始消息编号（会话存档的 msgid）；手工投递为"投递文件编号＋序号" |
| action | 是 | `send` 正常消息；`recall` 撤回事件 |
| conversation_type | 是 | `group` 群聊；`single` 单聊 |
| conversation_id | 是 | 群聊为 roomid；单聊为双方编号按字典序拼接 |
| conversation_name | 否 | 群名（摄取时的名称） |
| conversation_kind | 是 | 客户群、供应商群、内部群、混合群（来自名册） |
| client_id | 否 | 客户编号 C-NNN（来自名册） |
| project_ids | 否 | 项目编号列表；无法确定时为空 |
| attribution | 是 | `mapped` 映射确定；`suggested` AI 建议；`confirmed` 人工确认；`pending` 待归属 |
| sent_at | 是 | 发送时间，ISO 8601 格式，带 +08:00 |
| sender_id | 是 | 企业内为 userid，外部联系人为 external_userid |
| sender_person_id | 否 | 联系人编号 P-NNNN（来自名册） |
| sender_name | 否 | 显示名或名册里的称呼 |
| sender_org | 否 | 所属单位 |
| sender_role | 是 | 内部、客户、供应商、其他、未知 |
| msg_type | 是 | 归一后的类型：`text`、`image`、`voice`、`video`、`file`、`link`、`forward`（合并转发）、`mixed`、`card`、`location`、`doc`、`meeting`、`schedule`、`other` |
| raw_type | 是 | 会话存档原始的 msgtype |
| text | 否 | 文本内容；非文本消息填写识别、转写或抽取得到的文字 |
| text_origin | 否 | `original` 原文；`ocr` 图片识别；`asr` 语音转写；`extracted` 文件抽取；`caption` 标题与描述 |
| reply_to | 否 | 引用或回复的 record_id（能取到时） |
| mentions | 否 | 被 @ 的人员编号或 sender_id |
| attachments | 否 | 列表：file_name、file_type、size、checksum、storage_path、extracted_text_path |
| forwarded | 否 | 合并转发展开后的子消息列表（精简字段：sent_at、sender_name、msg_type、text） |
| recalled | 是 | 是否已被撤回；撤回事件关联到原消息，并把原消息标为 true |
| sensitivity | 是 | 数据级别初判 L1–L4（D01 第 9 章） |
| pii_types | 否 | 识别到的个人信息类型：证件号、手机号、银行卡、名单、健康、未成年人等 |
| masked_in_digest | 是 | 摘要中是否已遮蔽 |
| ingest_batch_id | 是 | 摄取批次编号，格式 IB-YYYYMMDD-HHMM |
| ingested_at | 是 | 摄取时间 |
| ext | 否 | 扩展字段（键值对）。新需求先放这里，稳定后再转为正式字段 |

## 5 名册：由业务方维护，摄取系统读取

### 5.1 群与项目映射（A08）

| 字段 | 说明 |
|---|---|
| conversation_id | 群的 roomid |
| 群简称 | 用于摘要文件名 |
| 群类型 | 客户群、供应商群、内部群、混合群 |
| 客户编号 | C-NNN |
| 活跃项目 | 一个或多个项目编号 |
| 默认项目 | 只有一个活跃项目时填写，消息直接归属 |
| 是否摄取 | 是、否 |
| 生效起止 | 映射的有效期 |
| 负责人 | 维护这条映射的项目经理 |

**维护规则**

- 建项目群时，由项目经理登记。
- 长期客户群（例如框架客户群）对应多个项目，只列在办项目；项目关闭后从"活跃项目"里移除。
- 出现有客户成员的新群但尚未登记时，摄取系统在批次清单里提醒负责人登记；登记前不摄取。

### 5.2 联系人名册（A08）

| 字段 | 说明 |
|---|---|
| person_id | P-NNNN |
| sender_id | userid 或 external_userid，可以有多个 |
| 称呼 | 摘要中显示的名字 |
| 单位 | 客户、供应商或本公司 |
| 角色 | 内部、客户、供应商、其他 |
| 关联 | 客户编号或资源编号 |
| 决策角色 | 如采购、业务对接、决策人、财务；可空 |
| 存档同意 | 来自企业微信的同意状态 |

## 6 归属规则

1. 群只有一个活跃项目：直接归属（`mapped`）。
2. 群有多个活跃项目：摄取系统先标为 `pending`；S01 根据内容（日期、地点、人数、项目名称、引用关系）提出归属建议（`suggested`），项目经理确认（`confirmed`）。
3. 无法判断的消息进入 `收件箱/待归属/`，每日提醒负责人处理。
4. 一条消息可以属于多个项目，例如同时提到两个订单。
5. 归属可以更正，更正记录保留。

---

## 7 媒体与特殊消息

| 类型 | 处理 |
|---|---|
| 图片 | 保存原件；做文字识别，重点是报价单、行程、名单的截图；识别的文字写入 text，标 `ocr` |
| 语音 | 保存原件；转码后转写（原件格式以接口为准），文字写入 text，标 `asr` |
| 视频 | 保存原件或链接；默认不转写【默认】 |
| 文件 | 保存原件；抽取文字（PDF、Word、Excel、PPT，扫描件做文字识别）；文件同时交给 S01 归档到项目的 01_原始资料 |
| 合并转发的聊天记录 | 展开为子消息，保留"转发自"信息 |
| 链接、小程序、卡片 | 记录标题、描述和地址 |
| 企业微信文档、日程、会议、待办 | 记录标题、时间和链接；文档内容按权限另行获取【预留】 |
| 撤回 | 原消息标 `recalled=true`；摘要中显示"[已撤回]"，不作为依据 |
| 表情、红包等 | 丢弃或只计数 |

处理失败时保留占位（例如"[图片识别失败，见原件]"），在批次清单中记录，下一批次重试。

---

## 8 敏感信息

- **识别**：证件号、手机号、银行卡号、成批的姓名名单、健康信息、未成年人信息。
- **在摘要中遮蔽**：证件号和银行卡号只保留后四位；手机号遮蔽中间四位；名单类文件在摘要里只写"名单文件（N 人），见原件"。
- **原件和原文**：只对授权人员开放，调阅留记录。
- **级别标签**：摄取时初判 L1–L4，人可以修正。

## 9 输出

### 9.1 统一消息记录

- 按日、按会话分文件，存放在摄取系统里，默认不复制到业务库【默认：AL3】。
- 供工具使用：检索、统计、重新生成摘要。

### 9.2 项目沟通摘要

- **位置**：项目工作区的 `02_沟通记录/`。
- **文件名**：`{YYYY-MM-DD}_{群简称}.md`；同一天的多个批次追加到同一个文件。
- 一个群对应多个项目时，每个项目的摘要只放归属于该项目的消息；待归属的消息放在 `收件箱/待归属/`。
- **格式示例**（人名均为示意）：

```
# 2026-11-12 某银行高峰会项目群

项目：2026-018　群类型：客户群　批次：IB-20261112-1800　消息数：37　最高级别：L4

[09:12] 王经理（客户·采购） 我们领导说人数可能要到 55 人，下周一前定  ‹r-8f2a›
[09:15] 小李（内部·项目经理） 收到，我们先按 55 人准备酒店备选  ‹r-8f2b›
[10:03] 王经理（客户·采购） [图片·识别] 会场平面图：主会场约 300 平方米……  ‹r-8f31›  〔原件：01_原始资料/2026-11-12_会场平面图.jpg〕
[11:40] 王经理（客户·采购） [文件] 参会名单（52 人），见原件  ‹r-8f40›  〔L4，已遮蔽〕
[14:22] 张总（客户·决策人） [已撤回]  ‹r-8f52›
```

### 9.3 待归属清单

`收件箱/待归属/{YYYY-MM-DD}.md`：消息、所在群、可能的项目、判断理由。

### 9.4 批次清单

每个批次一份：批次编号、时间范围、会话数、消息数、各类型数量、失败数、待归属数、新出现的未登记群。

## 10 时效与触发【默认】

| 方式 | 说明 |
|---|---|
| 定时批次 | 工作日每天两次（建议 12:00、18:00）；周末每天一次 |
| 按需拉取 | 收到"更新项目 018"时，拉取该项目映射会话在上一批次之后的新消息；目标是几分钟内完成 |
| 高频模式 | 项目处于"执行准备"或"执行中"阶段时，可以改为每小时一次【预留】 |

现场的紧急变更不等摄取：现场人员直接用口令发起 S06 快速影响检查，事后的摄取只负责补记录。

## 11 AI 侧的处理约定（S01）

- **输入**：上次处理位置之后的新摘要，加上项目主卡。处理位置记在主卡的"沟通记录已处理到"一栏（record_id 和时间）。
- **输出**：更新建议单（TP05），条目分两类：
  - **需确认**：影响当前条件的新信息（日期、人数、预算、地点、服务内容、硬性要求），以及决定、变更触发和待办；
  - **仅记录**：背景信息、偏好线索、资源与报价线索、一般沟通。
- 每条建议都带来源 record_id、建议的信息状态（默认"待确认"）和建议写入的位置（主卡、日志、报价记录、名册等）。
- 冲突（前后矛盾、不同人说法不一致）单独列出，必要时升级 T1。
- 摄取的内容永远不直接写入主卡；人确认后才写入。

## 13 其他渠道【预留】

- **手工投递**首批即可用：把截图、聊天导出、录音转写、会议纪要放进 `收件箱/手工投递/`，注明项目编号，由 S01 按同一格式处理（`source=manual`）。
- 邮件、飞书、电话录音系统接入时，只需要实现到统一消息记录的转换，S01 不用改。
- **腾讯会议录制**：会议录制如果已经通过乐享的连接器导入乐享，S01 可以从乐享读取纪要和转写，按手工投递处理（`source=meeting`）；见 D12 第 2 章。

## 14 依据与版本

- 字段设计参考了企业微信会话存档的公开开发资料，例如消息动作分为发送、撤回、切换，群聊用 roomid 标识，外部联系人用 external_userid 标识，同意和不同意存档有单独记录（参考：[WeWorkFinanceSDK 文档](https://pkg.go.dev/github.com/NICEXAI/WeWorkFinanceSDK)，第三方资料，以官方文档为准）。
- v0.1（2026-11-09）：初稿，字段为默认值，待与开发方对齐。
- v0.2（2026-11-09）：补充会议录制经乐享进入的渠道；X06 参考实现完成，合成样本测试通过（遮蔽、撤回、待归属、幂等）。
